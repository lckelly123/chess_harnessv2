# Chess research workspace

- Scope: the local React interface in `frontend/`; visitor mode is Operate. Match desk, Match library, and Positional testing are separate destinations in one persistent workspace shell.
- Audience and job: a harness developer watches matches, inspects a selected ply, revisits historical runs, filters the PostgreSQL position library for one turn, or runs a full training/test set and inspects its failures.
- Authority: the user pinned a modern black and purple redesign and delegated the remaining choices. The designer selected the analysis-workbench composition. Code is the system evidence; this pass created no separate concept card or visual comp.
- Direction: near-black graphite surfaces, violet actions and selections, lavender board squares, Archivo text, and one-pixel divisions. Root `DESIGN.md` and `.impeccable/design.json` replace the former cream/green ledger identity.
- First viewport: slim desktop navigation, complete board and replay transport, then selected explanation above compact chronology. New match expands setup; setup opens automatically when no match is selected. Historical browsing has its own library destination.
- Primary actions: choose white and black harnesses and a folder; start or stop a match; replay, scrub, and flip the board; select a trace ply; search, open, and refile records; create folders; filter and select a library position and harness; request one positional move; start a full-set queue or stop after its current position; inspect saved attempts, failures, and model passes.
- Harness choices: Baseline, Agent Player 1, Agent Player 2, and Agent Player 3. Positional testing resolves the four configured versioned IDs against the API and reports missing choices. Shared model controls stay in the shell and lock during a single-position run. Each queue captures its own harness and shared model selection when started; later control changes do not alter it.
- Content: typed harness, model, folder, match, position, player, trace, stored-PGN, one-turn-result, model-run, per-pass, and queue data from the existing FastAPI API. Positional summaries, run history, and queues come from PostgreSQL; dataset `v1` holds 400 positions, split equally between training and test. The component loads position summaries once on mount and reloads on Refresh or Retry. The queen-blunder PGN fixture is removed, with no file fallback. `README.md`, `docs/position-library.md`, and `docs/frontend-backend-contract.md` describe the API and data flow.
- Signature interaction: selecting a trace event selects its ply, synchronizes board and inspector, pauses playback, and enters replay mode. The inspector prefers the completed move event at that ply, then another move event, then the latest event. It presents the recorded explanation and disclosures for metadata and other events at that ply.
- Trace completeness: Moves and All events filters preserve ply groups. Every event remains accessible with timestamp, ply, player, phase, status, summary, stable ID, and recorded detail. Missing explanations have explicit empty states. Internal scrolling brings the selected group into view without moving the page or fighting routine polling.
- Library behavior: Match library opens with Agent vs agent and Positional testing buttons with explicit pressed states. Both views stay mounted to preserve browsing state when switching. Agent vs agent retains folders and search, adds visible timestamps and Newest first / Oldest first chronology, and opens records on Match desk for replay. Folder reassignment and pending/error feedback stay local to that row; harness versions unfold separately from the open action. The extension retains the graphite/violet/Archivo system and creates no separate visual comp.
- Positional-run library: Queue run selects all attempts, all queue runs, single runs only, or an exact historical queue. Position set, Engine analysis (Evaluated, Evaluation failed, Not evaluated), and Move grade are primary filters; More filters contains Dataset, Harness, Model, and Run status. Literal text search includes queue names and combines with these filters on the server before pagination. Queue choices and run rows show saved names when present, retaining set/ID labels for unnamed queues. Apply filters resets to the first of 30-run pages; Newest first / Oldest first controls chronology. Options include all historical queues and retired harnesses, and queue set/dataset filtering respects captured membership.
- Saved-run inspection: selecting an attempt shows its saved position before the move, proposed-move endpoints, and Flip board. The board's accessible label describes the position before the proposed move. The adjacent summary shows the chosen move, Stockfish grade, centipawn loss, expected-points loss, engine/depth, and better moves when recorded; emitted model passes and tool details follow. View queue runs scopes the library to that queue and resets pagination. Missing boards, moves, evaluations, scores, and passes have explicit states.
- Saved-run states: Clear filters, Refresh runs, loading, no runs, no matching runs, list/detail errors, unavailable filter options, and separate retry actions are explicit. Selected records remain selected after refresh when present on the resulting page. While the view is active, a list containing queued/running attempts polls every three seconds; selected queued/running details poll every two seconds.
- Position library: visible Set, Phase, Position type, and Side to move filters combine locally. More filters contains Dataset, Source, Puzzle theme, and Puzzle rating; search matches opening names, readable themes, and IDs. Results show 12 rows per page with a matching count and Previous/Next controls. Filter changes reset to the first page and select the first match; changing pages selects that page's first row. Rows and the board header show training/test, phase, and quiet/tactical tags. Rows also show side, dataset, available puzzle rating, and source game ID. The board exposes the source link, dataset, last move, rating or unrated status, themes, and a Position details disclosure for ID and FEN.
- Positional behavior: the first returned database position is selected on initial load, leading to the board, four supported harness choices, run command, and persisted attempt. The component stays mounted while navigation hides it, preserving filters, selection, in-flight request, and result. Loading, empty-library import prompt, no matching positions, unavailable, missing-harness, running, error, retry, and completed states are explicit. Refresh retains a selection that still matches the active filters, otherwise selects the first matching row or clears selection when none match. Position-library filters, pagination and refresh, position and harness selections, and shared model controls lock during a single-position run. Success outlines the proposed path on the unchanged board, labels its SAN, and selects the saved attempt in run history when it matches the active run filters.
- Full-set queues: Run a full set sits above the position workspace in the existing graphite/violet system. Position set, Dataset, and Queue harness controls define a new queue alongside the visible shared model. A full-width Queue name (optional) field above these controls accepts 120 characters. The backend normalizes whitespace and saves the name in every member's `config.queue.name`; blank/null names remain unnamed, duplicate names are allowed, and the UUID remains identity. Names organize runs without affecting execution. Run full queue shows the full split count (200 for either `v1` set) and ignores library filters. A single run or active queue disables starting another queue; an active queue disables single-run commands while position and trace browsing remain available. Loading, unavailable/retry, and command-error states are explicit.
- Queue progress: Recent queues selects a persisted queue, initially the newest. Saved names appear in this selector and the progress heading; unnamed queues retain their set/ID labels. Queue summaries and the selected detail poll every two seconds. The panel shows the full UUID labeled Full queue run, captured harness/model/dataset, status, attempted/completed/failed/waiting counts, a progress bar, and the current position. Stop after current immediately marks unstarted rows skipped while letting the active position finish. The failure count opens Positions and results with Show failures only selected; its visible chevron rotates with the disclosure. Results stay in a bounded, keyboard-scrollable list with ordinal, phase/type, status, move/classification, and recorded failure stage/message. Position and trace actions select the exercise and move keyboard focus and scroll to the board or exact linked run in Run history.
- Queue persistence: PostgreSQL stores each scheduled position directly in model_runs, grouped by nullable queue_tag; queue membership, progress, and outcomes are derived from those rows. There are only three positional tables: positions, model_runs, and model_run_passes. Each turn and its evaluation finish before the next begins. Validation, execution, evaluation, and timeout failures are flagged and later positions continue; a move classified as a blunder is a successful execution. A completed queue may include failed items. Browser closure does not stop the worker. Restart retains a saved completed grade, otherwise flags the interrupted attempt and continues pending positions without automatic replay. Runtime details live in `docs/position-library.md#full-set-queues`.
- Run history: the library and board stay above this Operate-mode extension, reached by View run history and inheriting the black/plum/Archivo system. The Position ID filter defaults to the selected exercise; exact Position ID, Run ID, and Queue tag filters combine, and All runs clears all three. Queue trace actions populate the position and run filters for the linked attempt. View queue runs in a run detail applies its queue UUID, clears the position and run filters, and returns to the first page. Results show 30 runs per page with Previous/Next controls and a selectable list of harness, model, status, run ID, timestamp, and chosen move. Tagged rows also show the queue name or Full queue run with the first eight UUID characters and the full UUID in the title. Refresh, loading, empty, failure, and retry states are explicit. The list updates every two seconds while a single-position request, full-set queue, or listed run is active; selected queued/running details also poll every two seconds. Unstarted rows show their creation time and an explicit queued message.
- Run inspection: a saved queue association adds its optional name, the same Full queue run label and full UUID as the queue summary, plus View queue runs; runs with no queue association omit this provenance. Chosen UCI move and Stockfish classification appear above the bounded, keyboard-scrollable model-pass timeline, with centipawn loss when available. Missing classification or CP fields read Not evaluated or No score recorded; mate comparisons can have a classification without CP loss. Every recorded pass exposes phase, status, timestamp, all emitted working notes, and errors; tool disclosures show arguments, results, errors, execution/rollback state, call ID, and available board context. Run details disclose IDs, configuration, and saved evaluation payload. Missing notes, moves, and passes have explicit states. Only emitted observations are presented, never inferred hidden reasoning.
- Raw model exchange: a secondary Expand action leaves positional pass summaries unchanged in Run history and the saved-run library. This Read inspection surface within the Operate workspace retains graphite/violet/Archivo, with no new visual world, comp, or assets. Input: and Output: form the reading view, with a sticky Back arrow above them.
- Exchange data and states: Input decodes the saved request JSON once, shows message roles and Markdown content with real newlines, and retains other request fields, tools, and unsupported content as JSON. Output renders every returned text/reasoning/refusal and native function-argument string as separate Markdown blocks in provider order, including repeats; absent output is blank. Headings, lists, tables, and code receive readable structure. Literal HTML/XML tags remain visible and inert; image references appear as text without image loads. Markdown may normalize prose whitespace, while saved snapshots and API payloads remain unchanged. Polling carries only `hasModelExchange`; the payload still loads on demand from `GET /api/positional-testing/runs/{runId}/passes/{passNumber}/exchange`. Uncaptured historical passes have disabled Expand actions. Opening feedback and fetch errors remain on the source card, with retry through Expand.
- Exchange navigation: the hidden workspace stays mounted. The sticky Back arrow, browser Back, or Escape restores the same pass, selected run, filters, timeline/document scroll, and source-action focus; entry focuses Input:. The `#model-pass/{runId}/{passNumber}` URL supports reload and Forward. A direct link without an in-app history entry returns locally to the workspace. Leaving during a pending request prevents its late response from opening the viewer.
- Constraints: the backend owns state and legal moves. React exposes no human move controls or inferred hidden reasoning. Folders are organizational metadata. A positional response uses the selected database row's exact stored PGN history, creates no match record, and never mutates that history. Ratings, themes, classifications, source metadata, and engine reference answers remain inspection/evaluation data and are excluded from the model's turn input. Detailed match graph execution remains in LangSmith. Positional attempts and passes persist automatically for all four harnesses in `model_runs` and `model_run_passes`. Successful Stockfish grading records the classification, expected-points loss, and strictly better legal-move targets; grading failure preserves the model trace and error. Existing runs are not backfilled.
- Responsive behavior: the desktop positional list is vertically bounded (510px) and scrollable; at 1250px and below its records scroll horizontally with four filter columns; below 1000px navigation moves above content; at 760px and below board/analysis and positional board/controls stack, positional filters return to two columns, and indexes scroll horizontally; below 480px setup, records, and replay reflow further. Run history has a desktop list/detail split, then horizontal run cards above detail at 760px and below. Its pass timeline is bounded at 650px on desktop and 560px on mobile. Explanation and trace regions remain bounded, metadata wraps, and focus stays visible.

At 760px, headings and stop controls stack, result outcomes move below the position text, and live-position actions wrap. Full queue UUIDs wrap within the queue summary and run detail, retaining the existing monospace metadata treatment. The results list remains bounded at 320px; errors wrap and board/history destinations show visible keyboard focus.
- Library responsiveness: desktop keeps the positional-run index beside its inspector, with board and outcome side by side. At 1250px, filters use two columns and outcomes follow the board; at 760px, the index sits above the inspector and is bounded at 360px; at 480px, filters become one column. Match records and the positional-run index are bounded, keyboard-scrollable regions; identifiers and result text wrap.
- Exchange responsiveness: the single-column reading canvas caps at 980px with 32px side padding, Archivo prose at 15px/1.75, and paragraphs and list items limited to 75ch. Input/Output headings are 24px; message roles are muted 14px labels, and code/JSON uses the existing monospace face. The sticky Back control is at least 44px high. At 760px and below, side padding becomes 16px, code padding/type become 12px, and source pass headers wrap. Long tokens and preformatted blocks wrap within the viewport; tables have a keyboard-focusable horizontal scroll region.
